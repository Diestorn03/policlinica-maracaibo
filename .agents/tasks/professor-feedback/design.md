# Diseño de implementación — feedback del profesor

**Estado:** revisión implementable que responde a `design-verdict.json` y `design-review.md`. Este documento no modifica código de aplicación, no descarta el borrador existente, no hace commit, push ni publicación.

## Summary

Esta iteración conserva la identidad visual y los contratos clínicos ya probados, pero corrige la jerarquía de la portada, el rail de servicios, la lectura de especialidades, la selección de piso/consultorio y la separación entre demostración estática y aplicación real. La demostración de GitHub Pages dejará de reutilizar el directorio importado o cualquier historial con apariencia de dato personal: se construirá exclusivamente con fixtures sintéticos controlados por el repositorio y una puerta automática impedirá publicar Pages si el artefacto todavía contiene el directorio/fotos importados o una capacidad de vídeo real.

La autenticación real sigue siendo exclusivamente la cookie HMAC, el middleware y D1 en Cloudflare Workers. En Pages, el selector de cuatro roles será una orientación de navegación claramente rotulada, con persistencia local limitada y explícita; no será una cuenta, ni autorización, ni una promesa de que los formularios se guardan. La videollamada real se limita a JaaS mediante la IFrame API oficial, JWT RS256 efímero emitido por el Worker y autorización por consulta; no se habilita en HTTP local, Pages ni mientras falten las puertas operativas, de privacidad y de proveedor.

**Suposiciones y puertas explícitas.** Las páginas públicas y la información institucional fija ya existente no se reclasifican en esta tarea. En cambio, no se presume autorización para el directorio, las fotos ni los historiales que hoy llegan de `0002_seed.sql`/`public/medicos`; esos materiales no formarán parte de Pages. La evaluación visual obligatoria es 1440×900 y 393×852. Antes de activar vídeo real se requiere una cuenta JaaS, AppID, `kid`, clave privada correspondiente, dominio Cloudflare HTTPS de prueba, política JaaS que exija JWT a cada participante y aprobación institucional de privacidad/proveedor. La ausencia de cualquiera bloquea vídeo real, pero no la demo estática sintética.

## Functional Requirements

1. La portada conservará un único `h2` visible cuyo texto DOM exacto sea `Estudios, cirugía y cuidados intensivos en un mismo edificio`. Estudios seguirá como filas comparables con nombre, nota e imagen; cirugía/unidades seguirá como grupo de tarjetas editoriales con contenido existente.
2. Cada `servicios/[slug]` mostrará todos los demás destinos de `indiceServicios` —incluida Especialidades cuando aplique— dentro de un `nav` semántico, usable sin JavaScript y mejorado progresivamente como rail horizontal.
3. Especialidades separará visualmente y semánticamente las que tienen médicos de las que todavía no los tienen, sin perder búsqueda sin acentos, checkbox, contador `aria-live`, estado vacío, enlaces al directorio ni lectura sin JavaScript.
4. La portada y el directorio calcularán piso, puertas y texto de ubicación mediante una única función canónica. Los datos estructurados válidos tendrán prioridad; el respaldo legado será determinista y conservará el registro histórico sin piso sin inventarle una ubicación.
5. Piso, consultorio y reset serán interacciones de botones nativos con estado programático, resultado anunciado y filtrado semántico. Los enlaces al directorio conservarán únicamente los parámetros existentes `q`, `esp` y `piso`, con `u()` y URL compartible.
6. En `PUBLIC_DEMO=1`, `/acceso/` ofrecerá solo «Abrir demo como administrador/médico/cliente/secretaría». No habrá credenciales, contraseña demo ni una afirmación de autenticación. Un rol inexistente o alterado vuelve a acceso demo y «Salir» elimina el estado local permitido.
7. La demo usará únicamente perfiles, consultas, turnos, nombres de interfaz, correos `.invalid` y avatares abstractos sintéticos definidos en el repositorio. No reutilizará las 125 fichas importadas, teléfonos, cédulas, direcciones, fechas de nacimiento, fotografías o historiales de la fuente productiva.
8. Fuera de demo, se preservarán sin cambio funcional el formulario real de `/acceso/`, `SESSION_SECRET`, la cookie `HttpOnly`/`Secure`/`SameSite=Lax`, el límite de inicio, middleware, rutas por rol y la alta exclusiva de clientes por Secretaría.
9. Solo el cliente propietario o el médico asignado a una consulta propia en estado `atendiendo` podrá pedir configuración de vídeo. El Worker comprobará la sesión, el rol, propiedad/asignación, estado y sala contra D1 en cada solicitud; el navegador no elegirá ni conservará sala, rol, dominio o token.
10. El vídeo real elegido será JaaS con IFrame API y JWT de un participante/sala, de 120 segundos y en memoria. No habrá formulario Jitsi, URL copiable, token visible, fallback a `meet.jit.si` ni emisión de token en Pages o Worker local HTTP.
11. Una consulta `atendiendo` con sala heredada no `pm-…` nunca recibirá JWT JaaS. Hasta que termine por el flujo actual, recibirá una transición recuperable; la habilitación de JaaS tendrá una precondición operativa de cero llamadas activas heredadas.

## Non-Functional Requirements

1. **Accesibilidad y teclado.** Los nuevos controles usarán HTML nativo donde sea posible, foco visible, etiquetas en español, `aria-pressed`/`aria-expanded` cuando proceda y regiones de estado para cambios dinámicos. `Enter` y `Space` serán los comportamientos nativos de los botones; las animaciones y scroll programático respetarán `prefers-reduced-motion`.
2. **Seguridad y privacidad.** No se persistirán en D1, HTML, URL, atributos DOM, almacenamiento web, artefacto Pages, capturas ni logs secretos de sesión/JaaS, claves privadas, JWT ni nuevos datos de configuración de vídeo. Los datos clínicos ya requeridos por el producto —incluidos identidad, motivo y diagnóstico— permanecen únicamente en las tablas D1 existentes, bajo la autorización actual de servidor; nunca se copian a Pages, URL, `localStorage`, atributos DOM, JWT/Jitsi `userInfo` ni logs de vídeo.
3. **Entornos honestos.** Pages es estático y no tiene cookie verificable, D1, middleware, API de Worker ni vídeo. `npm run dev` y `npm run preview` pueden validar sesión, roles y D1 local, pero `/api/video` rechazará HTTP antes de leer secretos o firmar. La integración de dos participantes se realizará exclusivamente en un Worker Cloudflare HTTPS de prueba con origen configurado.
4. **Responsive y calidad visual.** En 393×852 no habrá overflow horizontal del documento, texto crítico truncado, superposición de encabezados ni controles nuevos menores de 44 px. El único overflow horizontal intencional será el scroller interno del rail. En 1440×900 el ritmo de servicios, edificio, rail y jerarquías seguirá siendo legible sin vacíos accidentales.
5. **Integridad.** Se conservan las migraciones aplicadas, 125 médicos y datos importados en modo Worker, filtros `q`/`esp`/`piso`, consultorios A/B, la referencia histórica sin piso, una consulta activa por cliente, una atendida por médico y diagnóstico de 3–1000 caracteres. No se edita una migración histórica.
6. **Aislamiento de navegador.** En paneles Worker de vídeo habrá CSP y `Permissions-Policy` restrictivas con allowlist explícita de JaaS. Pages no cargará JaaS ni añadirá esas allowlists remotas.
7. **Dependencias y rendimiento.** La pila queda bloqueada como Astro 7.4.1, componentes `.astro`, TypeScript/JavaScript/CSS nativos, GSAP 3.15.0, Lenis 1.3.27, `@astrojs/cloudflare` 14.4.1, Cloudflare Workers/D1 y JaaS IFrame API. No se añade dependencia npm ni se modifica `package-lock.json`; JWT RS256 usa Web Crypto nativo. Si Web Crypto no pudiera cumplir la firma documentada, la implementación se detiene para pedir aprobación explícita de una dependencia con versión exacta; no se improvisa un paquete ni un rango abierto.

# Design

## Overview, visual direction and locked technology

La dirección visual no cambia de marca ni introduce un kit genérico de tarjetas. El sistema existente se mantiene deliberadamente: azul institucional `#014DB7`, marino `#24345F`, celeste de foco `#2EA3F2`, lavanda `#EDEFFA`, blanco `#FFFFFF` y línea `#E2E6F2`; Manrope continúa como única familia. El momento característico sigue siendo el corte arquitectónico del edificio, mientras la sección de servicios emplea ritmo de catálogo clínico —filas densas para estudios comparables y unidades con más aire—. El rail es un índice físico de servicios, no un carrusel SaaS: tarjetas discretas, borde/línea, imagen o símbolo existente, sin sombra repetida ni movimiento decorativo.

A 1440×900, el título de servicios ocupa una columna de 24–26 caracteres y la secuencia es encabezado, estudios, pausa moderada, unidades y enlace de especialidades. El edificio conserva corte a la izquierda y hoja de resultados a la derecha; la selección explícita tiene prioridad visual sobre el recorrido por scroll. El rail deja ver varias tarjetas y pone controles junto al encabezado. A 393×852, la fila de estudio conserva texto a la izquierda y foto 96×72 px a la derecha, unidades pasan a una columna y el rail usa tarjetas de aproximadamente 80vw dentro de su propio scroller. El edificio pasa a controles de ancho completo y una lista de resultados pertinente; acceso, reset y reintento pueden ocupar el ancho disponible.

La pila está bloqueada a la declarada en los requisitos. No habrá biblioteca de carrusel, autenticación, JWT, iconos, CSP ni Jitsi. La firma, el parser de fixtures y la auditoría usan APIs de Node/Web Crypto ya presentes. Esta decisión evita añadir superficie de cadena de suministro a una aplicación que maneja información clínica.

## Portada, edificio y filtros

En `index.astro`, `h2.servicios__t` pierde `data-split="lines"` para evitar que una animación corte u oculte el texto obligatorio. Conserva un único nodo `h2`, usa `text-wrap: balance`, un ancho contenido y una escala de `clamp` para separar encabezado, estudios, unidades y enlace final. Los enlaces y `alt` existentes se conservan. La distribución actual de estudios se mantiene en escritorio; en móvil se fija `min-width: 0` para la columna de texto y la imagen de 96×72 px. Unidades pasa de cuatro a dos y a una columna sin cambiar contenido.

`src/lib/ubicacion-medico.ts` será la única fuente de ubicación de UI. `puertasEstructuradas(consultorios)` convierte CSV en una lista ordenada por aparición: divide solo por coma, hace `trim`, mayúsculas y deduplicación, y acepta únicamente `^\d{1,3}[AB]?$`. `ubicacionDeMedico(m)` resuelve así: (1) `m.piso` tiene prioridad si pertenece a `PISOS`; si es vacío o inválido usa `ubicacion(m.consultorio).piso`; (2) un CSV no vacío y completamente válido tiene prioridad para puertas; (3) un CSV vacío usa las puertas del texto legado; (4) un CSV no vacío con token inválido devuelve cero puertas y marca el dato inválido, sin inventar o rescatar una puerta vieja; (5) si no hay piso, se conserva el texto legado y no se coloca el médico en otra planta. Un piso estructurado válido siempre gana sobre un texto legado que discrepe. Así el historial `C Nro.1` conserva su puerta/referencia, queda sin piso y no se fuerza en el corte.

La portada agrupa por `ubicacionDeMedico(m).piso` y muestra puertas de esa misma fuente. El directorio usa exactamente el mismo `piso` para el HTML servidor, `data-piso`, contadores y filtrado navegador. Si hay una puerta estructurada inválida, el médico sigue disponible por búsqueda/directorio, pero el edificio no la presenta como una puerta fiable. El enlace de nombre construye `u('/directorio/?q=…')` con `encodeURIComponent`; un contexto de piso añade solo `piso`, nunca un parámetro `puerta` inexistente.

`edificio.ts` modela `{ piso: Piso | '', puerta: string | '' }`. `seleccionarPiso` valida contra `PISOS`, fija piso y borra puerta; `seleccionarPuerta` valida que la puerta exista en el piso renderizado, fija ese piso y alterna la misma puerta a vacío; `limpiarEdificio` devuelve ambos vacíos. En el DOM, cada piso y puerta será botón nativo con `aria-pressed`; el estado único `#edificio-estado` será `role="status" aria-live="polite" tabindex="-1"` e indicará piso, puerta opcional y cantidad. Filas no coincidentes reciben `hidden`, no solo opacidad. Tras seleccionar se conserva foco en el botón activado. El reset exacto «Mostrar todos los médicos» aparece solo con selección, restituye `hidden`/estados y mueve foco al estado de resultados.

En escritorio, ScrollTrigger puede añadir una clase visual al piso que cruza el scroll únicamente cuando el reducer está vacío; no cambia `aria-pressed`, resultado ni estado manual. En móvil, un botón de piso abre su panel y cierra los no pertinentes; no se anida botón en `summary`. Sin JavaScript, los datos se renderizan completos y legibles. Con movimiento reducido no se hace scroll suave.

## JaaS: evidencia, configuración y autorización

Se elige JaaS gestionado, no `meet.jit.si` público ni Jitsi autogestionado. La evidencia ya registrada en `requirements-research.md` es la base de esta decisión: la [IFrame API oficial de Jitsi](https://jitsi.github.io/handbook/docs/dev-guide/dev-guide-iframe/) documenta `new JitsiMeetExternalAPI(domain, options)` y `roomName`, `userInfo`, `jwt`; la [integración IFrame de JaaS](https://developer.8x8.com/jaas/docs/iframe-api-integration) documenta `https://8x8.vc/<AppID>/external_api.js`, dominio `8x8.vc` y sala `<AppID>/<room>`; la [documentación oficial de JWT JaaS](https://developer.8x8.com/jaas/docs/api-keys-jwt/) documenta AppID, `room`, `exp`, contexto/rol y clave `kid`. Las guías oficiales Secure Domain/Token Authentication también advierten que JWT por sí solo puede dejar invitados anónimos tras crear una sala; por eso la cuenta JaaS debe demostrar antes de habilitarse que exige JWT para **cada** participante.

`src/env.d.ts` declara las cuatro variables opcionales. `JAAS_APP_ID` debe coincidir con `^[a-z0-9][a-z0-9-]{2,127}$`; `JAAS_KEY_ID` con `^[A-Za-z0-9_-]{1,128}$`; `JAAS_PRIVATE_KEY` se normaliza de `\\n`/CRLF a LF, exige delimitadores PKCS#8 `BEGIN/END PRIVATE KEY`, base64 válido y DER decodificado de 512 a 16 384 bytes; `JAAS_VIDEO_ORIGIN` debe ser un origen HTTPS sin usuario, ruta, query ni fragmento. `leerJaasConfig(raw)` es pura y devuelve exactamente una unión discriminada `missing | malformed | valid`, sin escribir valores a logs. Una clave que supera forma pero `crypto.subtle.importKey('pkcs8', … RSASSA-PKCS1-v1_5/SHA-256 …)` rechaza se clasifica como configuración malformada, no como 500.

Los secretos se cargan únicamente como secretos/bindings del Worker Cloudflare HTTPS de prueba y, más adelante, producción; nunca en `PUBLIC_*`, Pages, `dist`, D1, HTML, URL, logs, `.dev.vars.example` ni el repositorio. El ejemplo local explica que no se deben colocar allí porque local HTTP no emite tokens. `JAAS_VIDEO_ORIGIN` es el origen normalizado del Worker HTTPS de prueba/producción y permite una puerta comprobable: `api/video` devuelve 503 `video_solo_https` antes de leer clave o firmar si `request.url.protocol !== 'https:'` o si su origen no es igual al binding.

El JWT de cada solicitud autorizada se firma RS256 con Web Crypto y contiene header `{ alg: 'RS256', typ: 'JWT', kid }`, `aud: 'jitsi'`, `iss: 'chat'`, `sub: appId`, `room: salaOpacaExacta`, `nbf: ahora-5`, `iat: ahora`, `exp: ahora+120`, y `context.user` con ID aleatorio por emisión, nombre genérico «Médico»/«Paciente» y `moderator: true` solo para médico. No contiene ID D1, nombre, correo, avatar, teléfono, cédula, motivo, diagnóstico, sala wildcard o regex. Un reintento pide token nuevo únicamente si la consulta sigue autorizada y atendiendo.

`astro.config.mjs` inyecta `/api/video` solo fuera de `DEMO`; `middleware.ts` permite la ruta exclusivamente a `medico` y `cliente`, usando el 401 actual para API. La ruta permite solo `GET /api/video?consulta=<id>` y aplica una allowlist estricta antes de tocar D1: `entries.length === 1`, clave exactamente `consulta`, valor único `^[1-9]\d{0,9}$` y número no mayor de 2 147 483 647. Una clave desconocida, repetida, vacía o adicional recibe el mismo 400 `{ error: 'consulta_invalida' }` y no se lee.

`tele.ts` añade `autorizarVideo(db, actor)` después de su limpieza actual. Cliente solo coincide con `cliente_id`; médico solo con `medico_id`; inexistente o ajena da `not-found`; propia pero no `atendiendo` da `not-ready`; sala no `^pm-[a-z0-9]{24}$` da `legacy-room`; únicamente éxito entrega una sala interna al endpoint. `estado()` y `cola()` dejan de exponer `sala` al navegador. El dueño de sala sigue siendo `atender()`/D1; el dueño de diagnóstico y concurrencia sigue siendo `finalizar()`/D1.

La respuesta 200 es JSON `Cache-Control: no-store` con solo `{ domain: '8x8.vc', appId, room, jwt }`. El cliente conserva esos valores solo en variables hasta crear el iframe. La ruta mapea 400/401/404/409 esperables sin log de error; `legacy-room` usa 409 `{ error: 'sala_en_transicion' }`; HTTP local y config ausente/malformada usan 503 `{ error: 'video_no_configurado' | 'video_solo_https', referencia }`; una excepción D1 o firma tras configuración válida usa 500 `{ error: 'video_error', referencia }`. Solo 500/503 de configuración/firma/D1 se registran con operación, categoría, timestamp y referencia UUID, nunca consulta, sala, JWT, clave, nombre, correo, motivo ni diagnóstico.

La migración `0007_sala_jitsi.sql` puede conservar una sala `meet.jit.si` heredada en una consulta activa. La política elegida no la cancela ni la convierte automáticamente: antes de activar el secreto/flag JaaS, el operador ejecuta la consulta de preflight documentada `SELECT id, sala FROM consultas WHERE estado = 'atendiendo'` contra la D1 del entorno y valida que cada sala cumpla el regex canónico; la activación está bloqueada hasta que el conjunto de no coincidentes sea vacío por finalización/cancelación normal. Si apareciera una residual entre preflight y solicitud, recibe la transición 409 y copy «Esta consulta se inició antes de la actualización. La videollamada nueva no está disponible para ella; vuelve al panel o contacta a la clínica.» No hay JWT JaaS, 500 ambiguo ni mutación de historial. La fixture de migración existente se conserva y obtiene una prueba explícita de este caso.

## Cliente Jitsi, errores y cabeceras

`Videollamada.astro` recibe `consulta?: number`, no `sala`. En demo renderiza una limitación estática y no importa el script; en Worker contiene estado `role=status`, marco vacío y botón inicialmente oculto «Reintentar videollamada». Cliente y médico continúan sondeando `espera()`/`cola()`, pero solo actualizan `data-consulta`. `EnCurso.astro`, plantillas y HTML inicial dejan de llevar sala.

`jitsi.ts` valida primero que el ID DOM sea entero positivo y pide `GET /api/video?consulta=…` same-origin con credenciales. Trata 401 como retorno al acceso actual, 404/409/503 con textos concretos y 500 con referencia de soporte; nunca inserta el cuerpo de error como HTML. Valida tipos y formatos de la respuesta (`domain === '8x8.vc'`, AppID, sala canónica y JWT de tres segmentos base64url) antes de usarla. Carga una sola vez `https://8x8.vc/<AppID>/external_api.js` y construye `new JitsiMeetExternalAPI('8x8.vc', { roomName: '<AppID>/<room>', jwt, parentNode, width, height, userInfo: { displayName: 'Médico' | 'Paciente' } })` con la barra actual de cámara, micrófono, compartir pantalla, chat, mosaico, colgar y configuración.

Cada contenedor posee `AbortController`, contador de intento y `WeakMap` de API. Cambio de consulta, eliminación del contenedor, `pagehide` o reintento abortan fetch, llaman `dispose()`, vacían marco y descartan resultados tardíos. `videoConferenceJoined` oculta progreso; carga de script/iframe, `errorOccurred`, `cameraError`, `micError` o abandonar la conferencia muestran un estado español y reintento. Denegar cámara/micrófono es recuperable y no finaliza/cancela la consulta. No hay solicitud a `meet.jit.si` en ningún camino.

`cabeceras-seguridad.ts` define para las respuestas Worker de `/panel/` y `/medico/`: `Content-Security-Policy: default-src 'self'; base-uri 'self'; object-src 'none'; frame-ancestors 'none'; form-action 'self'; img-src 'self' data:; font-src 'self'; style-src 'self' 'unsafe-inline'; script-src 'self' https://8x8.vc; connect-src 'self' https://8x8.vc wss://8x8.vc; frame-src https://8x8.vc; media-src 'self'`; `Permissions-Policy: camera=(self "https://8x8.vc"), microphone=(self "https://8x8.vc"), display-capture=(self "https://8x8.vc"), fullscreen=(self "https://8x8.vc"), geolocation=(), payment=(), usb=()`; `Referrer-Policy: no-referrer`; y `X-Content-Type-Options: nosniff`. `/api/video` recibe la variante sin orígenes JaaS pero conserva `default-src 'self'`, `object-src 'none'`, `base-uri 'self'`, `frame-ancestors 'none'`, no-store y no-referrer. `style-src` conserva inline porque Astro emite estilos de componente; `script-src` no permite inline tras mover el script de arranque a módulo externo. Si JaaS necesitara otro origen distinto de estos dos, no se habilita: se actualiza el diseño/evidencia y se revisa la allowlist, nunca se usa wildcard. Middleware omite Pages prerenderizado, que no carga JaaS ni amplía políticas.

## Invariantes y estrategia de validación

| Invariante | Capa dueña | Razón |
|---|---|---|
| Fixture Pages no contiene datos importados personales | `d1Local(includeSeed:false)`, `demo-fixtures.ts`, hook de build y auditoría de `dist` | La UI/copy no basta para impedir fuga de datos. |
| Sesión real, activo/version y rol | `auth.ts`, `middleware.ts`, D1 | El navegador y `localStorage` son manipulables. |
| Alta exclusiva de cliente | `validarCliente()`/`usuarios.ts` en servidor | Campos HTTP ocultos/manipulados no pueden escalar privilegios. |
| Piso/puerta igual en portada/directorio | `ubicacion-medico.ts` | Evita que fuentes estructuradas y legado diverjan por pantalla. |
| Una consulta activa, una atendida, diagnóstico obligatorio | Índices D1, `tele.ts`, rutas actuales | Son reglas clínicas/concurrentes, no decisiones de UI. |
| Sala opaca y transición heredada | `atender()`, D1 y `autorizarVideo()` | Navegador no genera/elige sala ni convierte llamadas previas. |
| JWT de sala/actor/vida corta | `jaas.ts` y `/api/video` | Solo Worker HTTPS con clave puede firmar. |
| CSP y permisos de medio | `cabeceras-seguridad.ts` + middleware | Script/frame remoto necesita límites verificables. |
| Rol demo y persistencia limitada | `api.js`, acceso, layout, solo `DEMO` | Es UX, no seguridad ni sesión real. |

Las pruebas unitarias permanecen sin red externa. `tests/db.check.mjs` conserva migraciones, 125 médicos Worker, roles, Secretaría, consulta única y diagnóstico; añade fixtures demo sintéticas, ausencia de sala en formas públicas, autorización vídeo y regresión de sala heredada. `tests/sitio.check.mjs` cubre parser/reducer de ubicación y los casos de piso/puerta. `tests/video.check.mjs` genera una RSA temporal, verifica firma/claims/configuración y prueba cabeceras puras. `package.json` incorpora este archivo a `npm test` sin dependencia nueva.

La evidencia de build ejecuta `npm test`, `npm run build`, `npm run build:demo`, `git diff --check` y `git status --short`. La auditoría recorre texto de `dist`, comprueba ausencia de la carpeta de fotos importadas y de recursos/secretos de vídeo, y la revisión manual confirma que todos los nuevos enlaces usan la base de Pages. La evidencia visual usa el flujo existente de captura/navegador en 1440×900 y 393×852, con y sin reducción de movimiento, JavaScript desactivado para rail/especialidades/edificio, y teclado/lector de pantalla para foco, reset y estados.

La integración de vídeo es condicional: en local se demuestra 503 antes de firma; en Worker Cloudflare HTTPS de prueba se verifican cabeceras, solicitud de permisos, bloqueo de origen no listado y dos roles en la misma consulta. Las capturas/logs se sanitizan y no contienen token/PID clínico. Si falta AppID, clave, dominio, política de invitados o aprobación, el resultado se registra como bloqueado y la única publicación permitida sigue siendo Pages estático sintético/no clínico.
